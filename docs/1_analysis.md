# 1.2 АНАЛІЗ ІСНУЮЧИХ АНАЛОГІВ ТА ОБҐРУНТУВАННЯ ТЕХНОЛОГІЧНОГО СТЕКУ

У межах розробки кваліфікаційного проєкту проведено аналіз трьох представників існуючих ігрових та аналітичних систем з метою виявлення їхніх архітектурних обмежень і сформульовано вимоги до власного інженерного рішення.

## 1.2.1 Інженерний опис аналогів

### PokerStars
Проаналізовано систему, побудовану на основі гібридної монолітно-мікросервісної архітектури. Ігровий двигун (Game Logic Engine) реалізовано у вигляді стейтфул-моноліту на C++. Масштабованість досягається за рахунок горизонтального шардингу ігрових кімнат по окремих серверах.

Передачу даних реалізовано через бінарні TCP-протоколи із шифруванням для ігрового клієнта та REST API для зовнішніх сервісів. Збереження даних здійснюється у реляційних СУБД (Oracle, PostgreSQL) із партиціонуванням. Строга консистентність (ACID) забезпечується патерном 2PC (Two-Phase Commit).

Критичними інженерними обмеженнями системи є накопичений технічний борг legacy-коду, висока складність динамічного перерозподілу навантаження та підвищений ризик десинхронізації стану стейтфул-вузлів.

### GGPoker
Проаналізовано розподілену мікросервісну систему. Взаємодію між сервісами реалізовано через поєднання WebSockets для ігрових подій та gRPC для внутрішньосервісного обміну.

Стек даних включає NoSQL СУБД (MongoDB, Cassandra) для телеметрії, PostgreSQL для транзакцій та Redis/KeyDB для кешування сесій. Консистентність між сервісами забезпечується за моделями Eventual Consistency та патерном Saga.

Основними обмеженнями системи є високі затримки (Latency) при фоновому обчисленні складних аналітичних метрик під час пікових навантажень та висока вартість хмарної інфраструктури.

### PokerNow
Проаналізовано легковагове вебрішення на базі Event-Driven Node.js архітектури. Взаємодію з клієнтом повністю побудовано на протоколі WebSockets (Socket.io). Збереження стану виконується у NoSQL СУБД (MongoDB) з кешуванням у Redis.

Архітектурним обмеженням є однопотоковість середовища виконання Node.js Event Loop, що унеможливлює виконання важких математичних симуляцій у реальному часі без деградації швидкодії основного ігрового контуру.

На основі зібраних даних сформовано порівняльну матрицю систем за технічними критеріями.

## 1.2.3 Аналітичний висновок

Проведений системний аналіз показав, що існуючі рішення демонструють низку інженерних обмежень. Монолітні підходи та рішення на базі інтерпретованих однопотокових середовищ зіштовхуються із суттєвими труднощами при горизонтальному масштабуванні та проведенні обчислювально складних симуляцій у режимі реального часу. У той же час, класичні мікросервісні схеми із синхронною REST-взаємодією створюють додаткові затримки (latency bottleneck) при передачі телеметрії ігрових роздач.

Обрана в межах даного кваліфікаційного проєкту подієво-керована (Event-Driven) архітектура успішно нівелює вказані недоліки. Використання комбінації WebSockets для дуплексного зв'язку з клієнтом та gRPC для міжсервісної взаємодії забезпечує мінімальний рівень затримки передачі даних. Застосування Redis In-Memory гарантує консистентність ігрового стану зі швидкістю доступу <50ms, а винесення математичного розрахунку шансів у відокремлений паралельний двигун симуляцій Монте-Карло запобігає блокуванню основного ігрового циклу.

Інтеграція модулів Retrieval-Augmented Generation (RAG) та LLM дає можливість автоматизувати стратегічний аналіз ігрових сесій на основі логів, що виводить функціональність платформи поза межі стандартних статичних HUD-систем аналогів.
